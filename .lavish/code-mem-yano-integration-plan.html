Code-Mem autonomo, Yano come adapter

Il posto giusto per la memoria degli errori è Code-Mem. Yano deve inviare eventi strutturati e consumare le lesson, senza rendere Code-Mem dipendente da Yano.

Stato verificato

Code-Mem già presente

  • CLI modulare in src/, bundle distribuito in bin/cm.
  • cm init pi crea store locale, skill Pi e hook di sessione/risposta.
  • Esistono già cm save, cm recall, deduplica, lifecycle e cm consolidate.

Cosa manca per le failure

  • L’hook attuale salva soprattutto recall di sessione e messaggi completati.
  • Non esiste ancora un record strutturato nativo per errore, tentativo, causa e verifica.
  • Il prompt può guidare l’LLM, ma non deve essere l’unico meccanismo di rilevazione.

Integrazione Yano attuale

  • Yano invoca cm recall e cm query in modo bounded, con fallback se Code-Mem non è disponibile.
  • Ogni agente riceve la skill Yano Code-Mem.
  • Yano mantiene inoltre trace memory e memoria locale dell’agente: sono superfici diverse.

Disallineamento da sanare

Il repository locale dichiara versioni diverse:

  • src/globals.js e bundle: 0.6.0
  • package.json: 0.1.0
  • bin/package.json: 0.0.1
  • CLI globale osservata: 0.7.0

Modifiche nei due progetti

Repository Code-Mem — nucleo

  • Aggiungere un comando/API generico, per esempio cm record failure --json.
  • Persistenza strutturata con origine opzionale (yano, ci, manual).
  • Fingerprint, deduplica, privacy, stato observed → unresolved → resolved/obsolete.
  • Prompt/skill standalone aggiornato e hook best-effort.
  • Comando di refresh locale per aggiornare skill e hook dei progetti già inizializzati.

Repository Yano — adapter

  • Convertire eventi di tool/test/round falliti in record Code-Mem non bloccanti.
  • Passare metadati opzionali: task, ticket, run, round, ruolo, provider, file.
  • Recuperare le lesson pertinenti prima di un retry/escalation.
  • Conservare la trace Yano come evidenza completa: Code-Mem riceve una sintesi con provenienza.
  • Il planner segnala problemi di Yano a yano-local-pc; non modifica Yano autonomamente.

Distribuzione e aggiornamento

1. Code-Mem: modifica src/ → build bundle → test → sincronizza versioni → commit/push
2. Installazione globale: cm update (aggiorna CLI e skill user-level)
3. Yano: aggiorna adapter/skill/documentazione → test → bump → commit/push → npm update
4. Progetti esistenti: migrazione esplicita, senza cancellare memory/state.db
5. Verifica: cm version, yano doctor, test di cattura, recall e fallback

Il passo 4 deve diventare un comando esplicito e idempotente, ad esempio yano code-mem sync --all o un comando equivalente di Code-Mem. Il semplice cm update oggi aggiorna il CLI e le skill user-level, ma non è sufficiente per riscrivere automaticamente gli hook locali già presenti in ogni progetto.

Opzioni valutate

non sufficiente

B · hook + prompt

Rilevazione deterministica dell’evidenza, arricchimento semantico dell’LLM e fallback sicuro.

raccomandata

C · daemon sempre attivo

Più automatico, ma aumenta processi, consumo e complessità. Va valutato solo dopo B.

fase successiva

Rischi da chiudere prima del codice

  • Non salvare password, token, screenshot privati o dati personali.
  • Non trasformare ogni warning in una failure: servono segnali oggettivi o conferma dell’agente.
  • Non usare una failure non verificata come verità: deve rimanere observed.
  • Non rompere progetti già inizializzati: migrazione versionata, dry-run e nessuna cancellazione della memoria.
  • Tenere separati Code-Mem standalone, Yano trace e memoria operativa dell’agente.

Conclusione

Si può modificare Code-Mem da questa sessione. La modifica va fatta prima nel repository standalone; Yano va aggiornato dopo, solo per l’adapter e il consumo delle nuove API. Infine serve una migrazione idempotente per i progetti Yano già esistenti. Non è corretto affidare tutto al prompt: la soluzione raccomandata è hook deterministico + prompt + lesson verificata.
