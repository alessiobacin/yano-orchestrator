Decisione di prodotto

Tre livelli operativi, con costi leggibili

LivelloQuando usarloCoperturaRoster / parallelismoBudget iniziale
STANDARD Controllo periodico o pre-merge su un progetto conosciuto. Preflight, inventory meccanico, suite esistente, happy path e un caso d’errore per superficie critica; controlli log minimi. 1 qa-functional-verifier. Nessuna fan-out LLM; la scansione qa-inventory è uno script. ≤80 comandi · ≤150 file · 30m · 10k token
MEDIUM Audit di una release, di un modulo importante o di un’app con più superfici. Matrice canonica completa, test funzionali diretti e cross-command, sicurezza/dipendenze, benchmark mirati, E2E/a11y se esiste UI, verifica logging. qa-inventory-analyst → ondate da max 2: verifier + specialisti pertinenti. Parallelismo solo dopo gate umano. ≤180 comandi · ≤350 file · 75m · 24k token
DEEP Self-check di Yano, audit pre-produzione o rischio elevato. Tutto il medium + mutation/fuzzing isolato, flussi di recovery, stress/concorrenza, error injection, sicurezza approfondita, performance p50/p95/p99, retention/redaction log e full rerun. Team multi-agente a ondate max 2: verifier, security, dependency, speed, e2e/a11y, mutation. Sub-agent solo con roster/cap budget espliciti. ≤360 comandi · ≤700 file · 150m · 48k token

Nota: i budget sono guardrail, non una promessa di durata. Ogni limite consumato produce un report parziale con stato BLOCKED o UNKNOWN, mai un “pass” implicito.

Flusso rigido

Ogni risultato deve essere riproducibile

flowchart TD A[Scope + target + variant] --> B[Preflight: env, fixture, trace, baseline] B --> C[Inventory: docs, help, code, tests] C --> D{Standard?} D -- sì --> E[Verifier: suite + smoke + error path] D -- medium/deep --> F[Matrix canonica + grafo effetti] F --> G[Wave 1: functional + security] G --> H[Wave 2: performance + dependencies] H --> I{UI presente?} I -- sì --> J[E2E + a11y in env isolato] I -- no --> K[NA motivato] J --> L{Deep?} K --> L E --> M[Findings + severità + bug id] L -- sì --> N[Mutation/fuzz + recovery + log stress] L -- no --> M N --> M M --> O{Fix necessari?} O -- sì --> P[Planner: ticket → coder/reviewer] P --> Q[Full matrix rerun] Q --> O O -- no --> R[Gate: zero blocker + blocked/missing presentati]
01

Baseline

Versione, ambiente, dipendenze, test già presenti, fixture e limiti dichiarati.

02

Matrix

Atteso, comando, exit code, output, stato mutato e downstream da riverificare.

03

Evidence

PASS, FAIL, BLOCKED, NOT_IMPLEMENTED, NA; ogni finding ha riproduzione e severità.

04

Gate

Dopo i fix si riesegue tutto. Tre round rossi portano a escalation, non a loop infinito.

Logging e osservabilità

Il logging è una superficie da testare

GIÀ PRESENTE

Base Yano

  • trace JSONL per istanza e progetto
  • modalità events / standard / full
  • heartbeat applicativo
  • redazione chiavi sensibili
  • retention e rotazione giornaliera
MEDIUM

Cosa deve provare il QA

  • correlation id: run, round, ticket, assignment
  • start/end, durata, exit code, retry e timeout
  • stdout/stderr troncati con path evidenza
  • servizi mancanti classificati senza falsi FAIL
DEEP

Stress osservabilità

  • redaction negativa: nessun secret/PII nei log
  • recovery dopo crash/disconnessione
  • retention, permessi e limite disco
  • verifica che il log non alteri la logica
ⓘ
Regola di separazione

Se manca logging applicativo, il QA registra un finding “observability gap”. Il planner apre poi una remediation con observability-agent o coder: l’audit non inietta logging da solo nel worktree di verifica.

Verdetti e severità

Non confondere “non posso testare” con “è rotto”

VerdettoSignificatoImpatto sul gate
PASSAtteso e osservato coincidono, con evidenza.Nessun blocco.
FAILIl progetto si comporta diversamente dall’atteso o non propaga lo stato downstream.Se blocker/critical, impedisce la chiusura.
BLOCKEDPrerequisito, servizio, account o capability mancante; non è automaticamente un bug.Resta visibile e viene presentato all’utente.
NOT_IMPLEMENTEDLa capability è dichiarata ma non è stata trovata nel codice o nel runtime.Finding esplicito; decisione utente per nuovo lavoro.
NA / UNKNOWNNon applicabile oppure atteso non dimostrabile da una fonte verificabile.Mai convertito silenziosamente in PASS.

Ruoli

PROMPTS

Matrix + log

Aggiornare inventory/verifier con verdict, downstream delta, logging gates, isolamento e bounded retries.

TEST

Regression contract

Aggiungere smoke test per varianti, routing, budget, full rerun, blocked vs fail e nessun secret nei report.

DOCS

Allineare README, quick start, guide, catalogo, cheat-sheet, diagrammi, architecture e skill yano-cli.
